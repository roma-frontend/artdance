Дата: 1 сентября 2026. Документ фиксирует, **что выбрано и почему** — чтобы через
три месяца никто не переоткрывал закрытые вопросы.

## 1. Какая смета взята за основу

Во входных материалах три файла сметы, но содержательно их две:
`smeta-dance-platform.docx` и `Танцевальная платформа — предложение и смета.docx`
идентичны по содержанию (вторая — вёрстка первой).

| | Смета A `Dance_Platform_Project_Estimate` | Смета B `smeta-dance-platform` (× 2 файла) |
|---|---|---|
| Итог | ~8 000 000 AMD (≈ $21 900) | $9 400 – 13 100 (≈ 3 440 000 – 4 795 000 AMD) |
| Метод оценки | по модулям в AMD | по часам (345–465 ч × ставка) |
| Пакеты | MVP / FULL / PREMIUM | один объём |
| Платежи | Paynet (единый API) | банк-эквайринг + VPOS.am, с оговорками |
| Безопасность | отдельный раздел + требования | не выделена |
| Booking engine | разобран как отдельный модуль со сценариями | одна строка «45–60 ч» |
| Риски и допущения | 9 пунктов | 5 рекомендаций |
| Источники цен | 14 ссылок на официальные прайсы | частично |

**Выбрана смета A как коммерческая основа.** Причины:

1. **Разница в цене — 2,3×, и она обоснована именно сметой A, а не B.** B оценивает
   345–465 часов на систему, где один booking engine с проверкой доступности
   инструктора, зала, вместимости, переносов, отмен и возвратов реалистично стоит
   больше, чем отведённые ему 45–60 часов. Смета B недооценивает проект — она
   продаёт marketplace по цене каталога.
2. **Пакетирование.** Три уровня (MVP / FULL / PREMIUM) позволяют клиенту выбирать,
   а не отказываться. Без якорного PREMIUM цифра FULL выглядит как максимум;
   с ним — как разумная середина.
3. **Смета A аргументирует стоимость через риск.** Разделы про безопасность,
   webhook-идемпотентность, audit log и «redirect клиента не является
   доказательством оплаты» показывают заказчику, за что именно он платит.

**Что взято из сметы B и добавлено к A** (у B есть три вещи, которых у A нет):

- Реалистичная картина эквайринга: договор с банком (Америабанк, Ардшинбанк,
  Инекобанк, АКБА, IDBank) занимает 1–3 недели и комиссии не публикуются.
  Смета A называет только Paynet — этого недостаточно для планирования сроков.
- Сравнение альтернатив с плюсами/минусами (Clerk vs Supabase Auth, Cloudinary vs
  R2, Яндекс Карты vs Google Maps) — сильный материал для разговора с клиентом.
- Почасовая разбивка по 17 модулям — защита цифры при вопросе «почему так дорого».

Итоговое коммерческое предложение — в [`01-commercial-proposal.md`](./01-commercial-proposal.md).

| Валидация | Zod | 4.5.4 | одна схема на env, формы и API |

| Медиа | Cloudflare R2 | — | нет платы за egress, в отличие от Cloudinary с обрывом после free-лимита |

### Отклонения от смет — с обоснованием

**Аутентификация: Better Auth вместо Supabase Auth.** Обе сметы предлагают
Supabase Auth. Проблема: Supabase Auth держит пользователей в схеме `auth.users`,
недоступной Prisma напрямую, — приходится синхронизировать её с `public.User`
триггерами. Для платформы с четырьмя ролями, RBAC и audit log это лишний
источник расхождений. Better Auth хранит сессии и пользователей в нашей же схеме,
работает с Prisma, стоит $0 и не увозит персональные данные к третьей стороне.
Supabase остаётся как managed PostgreSQL со бэкапами — то есть от него берём то,
за что платим.

**Платежи: слой абстракции вместо жёсткой привязки к Paynet.**
См. `src/lib/payments/types.ts`. Бизнес-логика знает только интерфейс
`PaymentProvider`; конкретный провайдер выбирается переменной `PAYMENT_PROVIDER`.
Практическая ценность:

- Разработку checkout и booking можно начать **сегодня**, на `mock`-провайдере, не
  дожидаясь договора с банком. Это снимает главную блокировку по срокам, которую
  смета B оценивает в 1–3 недели ожидания.
- Можно подключить двух провайдеров одновременно: карты через банк-эквайрер,
  кошельки через агрегатор, и роутить платёж по способу оплаты.
- Смена банка не затрагивает ни одной строки в booking/checkout.

**Мультиязычный контент — отдельные таблицы, а не колонки `bio_ru`.**
`InstructorTranslation`, `VenueTranslation`, `DanceClassTranslation` и т.д.
Добавление четвёртого языка не потребует миграции всех таблиц каталога.

**Commission / Payout / Refund заложены в схему сразу.** Даже если в первой фазе
выплаты идут вручную. Смета A прямо рекомендует это, и рекомендация верная:
дописать marketplace-логику в существующую схему дешевле, чем переделывать
денежные таблицы на живых данных.

## 4. Доставка изображений: производные при загрузке, а не при показе

Решение принято до написания кода загрузки, потому что оно определяет и схему, и
счёт за хостинг.

В `next.config.ts` заданы `deviceSizes` и `formats: [avif, webp]` — это
оптимизация «по требованию» силами Next. Одновременно медиа-политика
предполагала генерацию вариантов при загрузке. Делать оба — двойная работа и
двойные деньги, поэтому роли разведены:

| Что | Как обслуживается | Почему так |
|---|---|---|
| **Загрузки пользователей** (фото инструкторов, залов, товаров) | конвейер `src/lib/media/ingest.ts` генерирует мастер + производные при загрузке, они лежат в R2 и отдаются CDN с иммутабельным кешем | исходник загружается один раз, а читается десятки тысяч раз. Трансформация на каждый показ платная и добавляет задержку первому посетителю каждого нового размера |
| **Ассеты репозитория** (`public/media/seed`, фоллбэки, OG) | один мастер в WebP + `next/image` | их немного, они кешируются на билде, и держать в git по пять производных на файл незачем |

Следствия, которые нужно помнить:

- в бакет **никогда** не попадает файл пользователя в исходном виде: EXIF с
  GPS-координатами удаляется, размер приводится к политике, контейнер
  пересобирается;
- ключ объекта содержит хеш содержимого, поэтому производные отдаются с
  `immutable` и годовым `max-age`, а инвалидация не нужна;
- **ошибки медиа-прокси не кешируются** — транзиентный 404 в CDN «залипает», и
  картинка остаётся битой после починки (грабли из `online-shop`);
- политика сжатия живёт в `src/config/media-processing.ts` отдельно от
  `media.ts`: последний читает `clientEnv`, а конвейер обязан работать в CI без
  окружения приложения.

Отклонено: `next/image` для пользовательских фото (платные трансформации на
каждый показ и лимит на исходник), а также загрузка «как есть» с обработкой при
первом обращении (первый посетитель ждёт энкодинг, а утечка EXIF уже произошла).

## 5. Фоновое видео первого экрана: петля в бакете, а не в репозитории

Версия прототипа от 02.09.2026 заменила статичный hero фоновым видео. Исходник
`dancer-fhd.mp4` весит **21,6 МБ** и подключён как `autoplay muted loop` без
`poster` и без `preload`, плюс трейл создаёт до шести копий `<video>`.

Принято:

| Решение | Почему |
|---|---|
| Видео **не коммитится в git** | Git хранит бинарники в истории навсегда: 21 МБ добавились бы к каждому клону и каждому CI-прогону до конца жизни проекта. Место такого файла — объектное хранилище |
| **Две версии кадра**: 1280 и 1920 | На мониторе 1440 единственная версия в 1280 растягивалась в полтора раза: первый экран выглядел мыльным при формально настроенном битрейте, и никакой битрейт этого не лечил. Обратная сторона — телефон, где кадр занимает около 560 пикселей: ему версия 1920 была бы мегабайтом, скачанным впустую, поэтому он получает 1280. С 05.09.2026 у широкой версии есть и вторая роль — запас на хвостовое укрупнение кадра (1920 / 1.3 = 1477 исходных точек против 1440 экранных) |
| Клип 10 с, без звука, бюджет 2,4 МБ на файл | Это первый экран: трафик тратится до того, как пользователь увидел хоть одно слово. Десять секунд — весь ход камеры в присланном клипе; резать нельзя, иначе сцена не открывается до конца. Платит бюджет не каждый: браузер скачивает ОДИН файл, типичный десктоп берёт AV1 (785 KB), телефон — узкую версию (638 KB), а самый тяжёлый H.264 достаётся только браузерам без AV1 и VP9 |
| Три формата: AV1 → VP9 → H.264 | AV1 даёт тот же результат вдвое дешевле по трафику, H.264 остаётся фоллбэком для старых Safari. Замерено на этом клипе: SSIM всех трёх — 0.991–0.992 против исходника, то есть визуально неотличимо, и AV1 при этом самый лёгкий |
| Постер — **первый кадр самого клипа** (`hero-loop-poster`) | Прежним постером был `hero-dancer` из папки прототипа, и это оказалось двумя дефектами сразу: SSIM между ним и первым кадром — 0.86, то есть другой момент съёмки (при старте был виден скачок), плюс файл всего 1672 пикселя шириной. `hero-dancer` остаётся в манифесте ассетов — это файл утверждённого прототипа |
| В имени файла ассета — **отпечаток содержимого** (`hero-loop-poster.f3395db5.webp`) | Имя было производно только от семантического имени, поэтому замена содержимого не меняла URL. По URL кешируют трое: браузер, CDN и оптимизатор изображений Next (`.next/cache/images`). После подмены постера первого экрана страница целую секунду показывала кадр из ПРОШЛОГО макета. Отпечаток в query не годится: Next 16 отклоняет локальные изображения с query-строкой, не описанной в `images.localPatterns`, а описать там произвольный отпечаток нечем — сравнение точное |
| Автозапуск подавляется при `prefers-reduced-motion`, `Save-Data` и 2G | Это не деградация, а исполнение явной настройки пользователя. Остаётся постер — закрытый занавес со светящейся щелью, законный кадр первого экрана |
| Трейл копий кадра (`hero-ghosts`) **удалён** 05.09.2026 | Эффект множил отстающие снимки ИГРАЮЩЕЙ петли: смысл был в следе за движущейся фигурой. С переходом на раскрытие прокруткой играть стало нечему — кадр стоит, пока страницу не крутят, и шесть копий одного кадра читаются как дефект отрисовки. Убран целиком, а не выключен параметром: выключенный параметр оставил бы код, который никогда не исполняется |
| Кнопки паузы нет и не требуется | WCAG 2.2.2 говорит об анимации, которая запускается САМА. Здесь движения без действия пользователя не происходит вовсе: клип стоит на первом кадре, пока не будет жеста прокрутки |

## 8b. Раскрытие занавеса на первом экране (05.09.2026)

Первый экран заменён по решению заказчика: вместо фоновой петли — «занавес
открывается». Жест прокрутки запускает раскрытие, оно доигрывает до конца само,
и последний кадр совпадает с приходом второй секции.

Принято:

| Решение | Почему |
|---|---|
| Раскрытие делает ПРОКРУТКА, а не видео | Получить раскрытие от генератора видео не удалось, и причина не в формулировке промпта: на вход модель получала кадр с закрытым занавесом и убрать его из пикселей не могла — только отъехать камерой. На 10 и на 15 секундах результат один: занавес открывается частично. Побочная выгода важнее исходной задачи — «сделайте быстрее» стало правкой одного числа, а не новой генерацией |
| Зум в щель отклонён | Щель занимает 13% ширины кадра (замерено по столбцам яркости). Чтобы она заполнила окно, нужно семикратное увеличение: полоса в 270 пикселей растянулась бы на всю ширину |
| Клип ИГРАЕТ, прокрутка следует за его временем | Обратный порядок был сделан и отвергнут. Прокрутка, ведущая клип, — это перемотка: каждое положение страницы даёт запрос `currentTime`, то есть сборку кадра по требованию. Таких запросов десятки в секунду, выполняются они неравномерно, и движение читается как перелистывание. Плавно видео умеет только одно: играть. Побочная выгода: синхронность держится сама — если браузер срежет скорость или клип встанет на буферизации, прокрутка встанет вместе с ним |
| Обратный проход — **отдельный перевёрнутый клип** (`hero-loop-reverse`) | Назад воспроизвести нельзя: отрицательной скорости у видео не бывает. Перемотка назад была сделана и отвергнута — при ключевом кадре каждые 8 кадров задержка перемотки колеблется с тем же периодом, и движение «местами ускоряется, местами замедляется». Перевёрнутый клип играется вперёд, то есть плавен по той же причине, что прямой. Качается лениво, с началом прямого прохода: тот, кто первый экран не тронул, за него не платит |
| Жест ОТМЕНЯЕТСЯ (`passive: false`), а не наблюдается | Пассивный слушатель браузер не ждёт: при резком жесте страница успевала уехать раньше, чем начинался проход, и первый кадр возвращал её назад — рывок тем сильнее, чем резче жест, и заметный только на обратном проходе, потому что вперёд обе силы тянут в одну сторону. Тем же перехватом закрывается «остановить на середине нельзя»: промежуточных положений в замысле нет |
| Геометрия замеряется вне цикла кадров | Замер внутри цикла давал обратную связь «замерил → сдвинул → замерил уже другое»: положение обёртки зависит от прокрутки, браузер округляет её до целых пикселей, и цель смещалась на доли пикселя туда-обратно. На шве секций это читалось как дрожание кромок. По той же причине цель округляется до целого пикселя, а на время прохода выключается `overflow-anchor` |
| Текст первого экрана НЕ двигается и НЕ гаснет | Решение заказчика. Ход текста читался как отдельное движение, спорящее с раскрытием. Следствие: вуаль под текстом не растворяется, а ГУСТЕЕТ — к концу за текстом открытая сцена, самая светлая часть кадра, и ivory-заголовок на ней потерял бы контраст |
| Первый экран приколот, обёртка выше окна на одну его высоту | Раскрытию нужен ход прокрутки. Без него занавес открывался бы уже за кромкой окна — то есть ровно тот дефект, из-за которого раскрытие и вынесли из видео в прокрутку |
| Состояние шапки следует за первым экраном, а не за порогом в 60px | Порог был верен, пока экран уезжал сразу. С приколотым экраном он красил шапку в цвет канвы, когда за ней ещё на два экрана вперёд тёмный театр |

Отклонено: снап по времени (доигрывание по часам — обратный проход «ускорялся»),
отдельная фаза доезда до второй секции (получались два движения подряд: видео
кончилось, потом страница поехала), удержание прокрутки без предохранителя
(клип на буферизации оставил бы страницу заблокированной).


Команды кодирования собирает `scripts/encode-video-loops.ts` из политики
`videoLoopPolicy` — параметры меняются вместе с бюджетом, а не отдельно от него.
Готовых строк `ffmpeg` в конфиге больше нет: они дублировали скрипт и с
появлением второй петли (§8) стали прямо неверными. Требуется `ffmpeg` — на
машине разработчика его может не быть, тогда шаг выполняется отдельно.

Отклонено: подключение исходника как есть (первый экран весом в 21 МБ),
`<video>` без постера (пустой кадр вместо LCP), Cloudflare Stream для этой петли
(это фон, а не контент — плеер, аналитика и подписанные URL здесь не нужны и
стоят денег; Stream остаётся для видеокурсов Фазы 3).

## 7. Акцент бренда: бургунди в обеих темах, WCAG-отклонение принято

**Решение заказчика от 04.09.2026. Вопрос закрыт — переоткрывать его правкой
палитры нельзя.**

Акцент платформы — бургунди `#8B1A2B`, наведение `#6E1422`. Один и тот же цвет
в светлой и тёмной темах и на любом фоне, включая кинематографичные плоскости
(hero, editorial). Так он объявлен в утверждённом прототипе: `--accent` живёт в
`:root` и в `[data-theme="dark"]` не переопределяется.

Что было предложено и отклонено:

| Вариант | Контраст на почти чёрном | Почему отклонён |
|---|---|---|
| Осветлить бургунди по постоянному тону (`#E58C99`) | 6.0:1 | получается розовый; заказчик отклонил дважды |
| Отдать акцент на тёмном золоту `#B89A5E` | 7.4:1 | «золото» не акцент бренда; в прототипе им окрашены только надзаголовки и показатели |
| Оставить бургунди | **2.15:1** | **принято** |

Цена решения измерена и признана: как ЦВЕТ ТЕКСТА на тёмных подложках бургунди
даёт 1.3–2.2:1 вместо 4.5:1 (WCAG 1.4.3), рамка фокуса в тёмной теме — 1.8–2.2:1
вместо 3:1 (1.4.11). Обойти это подбором оттенка невозможно: чтобы бургунди дал
4.5:1, подложка должна быть светло-серой.

Как это зафиксировано в коде, чтобы не всплывало заново:

- список принятых пар — `isAcceptedLowContrast` в `src/design/tokens/contrast.ts`
  вместе с причиной и датой;
- у этих пар `contrast.test.ts` проверяет не порог, а то, что **цвет не менялся**:
  случайная правка палитры по-прежнему падает тестом;
- axe в `e2e/accessibility.spec.ts` отбрасывает только те узлы, где цветом текста
  стоит именно брендовый бургунди. Правило `color-contrast` не отключено —
  любая другая плохая пара валит проверку;
- список закрытый: пара, которой в нём нет, обязана проходить порог.

Если решение когда-нибудь пересмотрят, менять нужно палитру И этот список
одновременно — иначе тест сообщит о расхождении.

## 8. Вторая фоновая петля: видео в editorial-секции вместо статичного кадра

**Просьба заказчика от 04.09.2026.** В утверждённом прототипе фон секции
«EVERY BODY HAS A RHYTHM. FIND YOURS.» — статичная фотография (`.editorial-bg >
img`). Заказчик прислал клип и попросил поставить его туда. Это отклонение от
макета, поэтому оно зафиксировано здесь, а не решено молча.

Исходник — сгенерированный клип, 1280×720, 24 fps, 10 с, 2,9 МБ, со звуковой
дорожкой. Два дефекта, которые в таком виде попали бы на страницу:

| Дефект | Как виден | Решение |
|---|---|---|
| Знак генератора видео (звезда) в правом нижнем углу | светлее фона, затемняющий слой его не скрывает | `delogo` заклеивает прямоугольник интерполяцией. Обрезка не годится: знак отстоит от края на десятую часть кадра, композиция уехала бы |
| Клип не является петлёй: последний кадр не совпадает с первым | скачок каждые 8,5 секунды, в полноэкранной секции заметнее всего остального | хвост 1,5 с растворяется в начало (`xfade`), петля замыкается сама на себя. Цена — полторы секунды исходника |
| Звуковая дорожка | лишний вес, петля всё равно `muted` | удаляется при кодировании |

Оба параметра — данные политики `videoProcessing.editorialLoop`, а не правки
файла руками: при замене клипа они меняются в конфиге, а не в бинарнике.

Принято по самой петле:

| Решение | Почему |
|---|---|
| Бюджет 2,4 МБ на файл | кадр открыт на полную (иначе клип превращался в тёмное пятно), а открытый кадр требует битрейта: тёмные градиенты и боке-частицы — худший материал для сжатия, и на 850 kbit/s они распадались на полосы. Исходник сам сжат до ~3 Mbit/s, кодировать его втрое ниже значит накладывать вторые потери на первые. Замерено после исправления: PSNR 43.5 dB и SSIM 0.979 против исходника вместо 40.1 dB и 0.968 |
| Две версии кадра: 720 и 1280 | здесь кадр рисуется ровно по ширине окна (обёртки со сдвигом, как у hero, нет), поэтому широкой версии достаточно 1280 при исходнике 1280 — апскейла на десктопе почти нет. Узкая версия существует ради телефонов: им незачем качать кадр вчетверо шире, чем они его показывают |
| Файл начинает качаться за один экран до появления, а не при загрузке страницы | до секции могут не долистать, а трафик платят все. Проверяется по сетевым запросам в `e2e/editorial-video.spec.ts` |
| Имя файла содержит ширину версии и отпечаток содержимого (`editorial-loop-1280-a0a10445.mp4`) | под постоянным именем замена клипа не меняет URL, и браузер, CDN и кеш сборки продолжают отдавать ПРЕЖНЕЕ видео. Проверить, что клип сменился, тогда нечем, кроме глаз, а два клипа с одной съёмки на глаз неразличимы. Это не теория: на постере и в браузере заказчика ровно так и произошло |
| Постер — **первый кадр самой петли** (`editorial-loop-poster`, 20 KB), снятый с графа фильтров до сжатия | подмена постера видео не читается как смена картинки: кадр просто оживает. Кадр берётся не из готового AV1-файла, а из графа: в браузере может играть любой из трёх форматов, и привязывать постер к артефактам одного кодека неправильно. Совпадение проверено — PSNR 38–43 dB против первого кадра каждого формата, то есть отличие только в потерях самих кодеков. Прежний `editorial-rhythm` светлый и тёплый, а петля — тёмная сцена в бордо; переход между ними был бы виден |
| Шлейфа копий, как у hero, нет | это второй набор декодов ради эффекта, который в короткой секции не читается |
| `blur()` на видео нет, хотя у постера он есть | у постера размытие скрывает артефакты одного кадра; у петли это фильтр на каждый кадр во весь экран — самая дорогая операция композитора из возможных здесь |
| Кадр растворяется к краям маской `mask.cinemaEdges` | секция чёрная, кадр — нет. Без маски у видео видны четыре кромки и оно читается как вставленное окно, а не как фон |
| Добавлен второй scrim под текстом (`scrim.editorialCopy`) | у фотографии яркость за заголовком постоянна, у петли меняется каждый кадр: в момент прохода контрового света ivory-текст терял контраст. Вуаль его гарантирует и попутно собирает взгляд к центру |
| Кнопки паузы нет | то же решение, что у первого экрана (§5): роль управления движением выполняет системная настройка, при `prefers-reduced-motion` и `Save-Data` остаётся постер — то есть ровно макет |

Отклонено: живое видео без маски и вуали (кадр-окно в чёрной секции и
плавающий контраст заголовка); тонирование кадра в брендовый бордо
`mix-blend-mode` (клип уже снят в этой палитре — танцовщица в бордовом платье
под красным контровым светом, тонирование только грязнило бы тени); палиндром
вместо растворения шва (обратное движение танца читается как «видео назад»);
загрузка петли вместе со страницей (полмегабайта тем, кто до секции не дошёл).

Побочный результат, полезный дальше: видеоконвейер перестал быть привязан к
первому экрану. Петли перечислены в реестре `videoLoopPolicy`, кодирует их один
скрипт `npm run video:encode -- --loop <петля> --input <файл>`, а бюджет каждой
проверяется своим порогом. Третья петля — одна строка в реестре.

Имена файлов содержат отпечаток содержимого, и у этого есть два следствия в
работе. Во-первых, `npm run video:encode` удаляет прежние файлы петли перед
кодированием: новый файл не перезаписывает старый, они бы накопились, и
`video:check` сообщил бы о двух файлах одного формата. Во-вторых, для файлов,
исходников которых в репозитории нет (петля первого экрана — 21,6 МБ), есть
`npm run video:encode -- --relink`: он переводит уже лежащие файлы на имена с
отпечатком и пересобирает манифест, ничего не перекодируя. Тем же флагом
восстанавливается потерянный манифест — он собирается из того, что действительно
лежит в папке.

Что осталось известным ограничением: постер лежит под постоянным именем
(`editorial-loop-poster.webp`), потому что имена сид-ассетов — общая конвенция
конвейера изображений. После замены клипа локальный кеш `next/image` продолжает
отдавать прежний постер, и его надо сбросить:
`Remove-Item -Recurse -Force .next\cache\images`. В production этого нет: медиа
уходит в R2 с ключами по хешу содержимого.
