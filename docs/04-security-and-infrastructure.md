# Безопасность и инфраструктура

Документ фиксирует, **что перенято из существующих проектов** (`builder-studio`,
`office`, `online-shop`), что сознательно НЕ перенято, и что осталось сделать.

Каждое решение здесь — реакция на конкретную ошибку, которую эти три проекта уже
совершили и исправили. Формулировки «почему» важнее списка файлов: без них
следующий разработчик уберёт защиту, приняв её за перестраховку.

---

## 1. Что перенято

### 1.1 Один edge-слой безопасности — `src/proxy.ts`

Пять задач в одном проходе, без обращений к БД: security-заголовки и CSP,
CSRF через `Origin`, backstop rate limit на `/api`, локализация URL, гейт
приватных разделов.

**Главное правило, зафиксированное жёстко:** security-заголовки живут ТОЛЬКО
в `proxy.ts`, а `next.config.ts` отвечает исключительно за `Cache-Control`.
Когда заголовки задаются в двух местах, они конфликтуют, и отладка превращается
в угадывание, какой слой победил.

Источник: `office/src/proxy.ts`, `builder-studio/proxy.ts`.

### 1.2 CSP без nonce — осознанный компромисс

Взято из `online-shop`. Nonce требует динамического рендеринга каждой страницы;
публичный каталог ArtDance (занятия, инструкторы, площадки, товары) обязан
отдаваться с CDN без вызова serverless-функции. Цена — необходимый
`'unsafe-inline'` для inline-бутстрапа Next.js.

Дополнительно перенята идея **двух политик**: страницы входа и регистрации
получают ослабленную CSP (`'unsafe-eval'` для виджетов сторонней авторизации),
остальной сайт — строгую. Ослаблять политику всего сайта ради двух страниц —
типичная ошибка.

Если появится требование строгого CSP — переходить на `'strict-dynamic'` + nonce
и одновременно отказываться от CDN-кеша HTML. Это торговля, а не улучшение.

### 1.3 CSRF через `Origin`, без токенов

Перенято из `builder-studio`. Браузер всегда присылает `Origin` на cross-site
мутирующем запросе; клиент без `Origin` (server-to-server, curl) не носит cookies
и потому не может воспользоваться чужой сессией.

Дешевле signed double-submit (который есть в `office`), не требует хранения
состояния и не ломается при истечении токена в открытой вкладке. Webhook-пути
исключены: подпись сама себе аутентификация.

Проверено живьём: `npm run verify:headers` отправляет `POST` с чужим `Origin`
и требует 403.

### 1.4 Rate limiting: fail closed в production

`src/lib/security/rate-limit.ts`. Самое важное решение здесь взято из `office`:
**если Redis недоступен, чувствительный запрос отклоняется**, а не пропускается.
Иначе падение Redis автоматически снимает всю защиту от брутфорса — отказ
инфраструктуры превращается в дыру.

Разделение, которого не было ни в одном из трёх проектов:

| Что | Поведение при недоступном Redis |
|---|---|
| Логин, платежи, брони, OTP | **fail closed** — отклоняем |
| Флуд-backstop на `/api` | **fail open** — пропускаем |

Флуд-backstop защищает от шума, а не от целевой атаки, и его отказ не должен
ронять весь сайт. Точечные лимиты остаются строгими.

Реализация на голом `fetch` к Upstash REST: работает и в Node, и в Edge (нужно
для `proxy.ts`), не тянет SDK в бандл. Лимиты берутся из `rateLimits` в
`@/config/business` — по логической операции, а не по URL, чтобы выживать
рефакторинг роутов.

### 1.5 RBAC: capability-матрица с временными грантами

`src/config/capabilities.ts`, `src/lib/auth/capabilities.ts`,
`src/lib/auth/guards.ts`. Модель взята из `builder-studio/lib/access.ts` и
`online-shop/convex/lib/auth.ts`.

Три правила, каждое из которых предотвращает конкретный отказ:

1. **Отсутствие записи в матрице = разрешено.** Новая capability не ломает
   поведение существующих админов.
2. **ADMIN никогда не ограничивается.** Иначе неверная запись в матрице способна
   запереть владельца платформы вне админки.
3. **Временный грант перекрывает запрет.** Выдать доступ на два часа вместо смены
   роли навсегда — это то, что реально происходит в поддержке. Гранты на деньги
   и роли запрещены (`nonGrantableCapabilities`).

Плюс лестница гвардов: `requireCaller` → `requireRole` → `requireCapability` →
`assertOwnership` / `requireInstructorProfile` / `requireVenueMembership`.
Последние три — механизм «инструктор редактирует своё занятие не по праву,
а по владению», прямой аналог изоляции продавца в `online-shop`.

**Ключевой принцип, вынесенный в комментарий модуля:** каждый `'use server'`
экспорт — это публичный HTTP-эндпоинт. Отсутствие гварда в первой строке
означает открытый доступ.

### 1.6 Audit log, который не может сломать операцию

`src/lib/audit.ts`. Из `builder-studio/lib/audit.ts` и `online-shop`:

- **никогда не бросает** — сбой журнала не отменяет подтверждение оплаченной брони;
- **снапшоты `before`/`after`** делают запись откатываемой без event sourcing;
  `revertedAt` не даёт откатить дважды;
- **`actorEmail` дублируется строкой** — журнал остаётся читаемым после удаления
  аккаунта;
- **критичные действия** (`criticalAuditActions`) дублируются оповещением
  владельцу. Список короткий намеренно: если алертов много, их перестают читать.

Добавлено сверх источников: **маскировка PII в снапшотах**. Журнал читают
сотрудники поддержки, а не только владелец, поэтому пароли и токены заменяются
на `[redacted]`, email и телефон — частично.

### 1.7 Валидация загрузок

`src/lib/security/uploads.ts`, политики в `src/config/security.ts`.
Из `office/src/lib/security.ts`. Модель угроз:

1. **MIME и расширение подделываются независимо** — проверяются оба.
2. **Разделители пути в имени** позволяют вырваться из папки хранилища через
   ключ объекта — отсекаются до разбора расширения.
3. **Размер проверяется по `Content-Length` до чтения тела** — иначе 512 MB
   попадают в память ещё до отклонения.
4. Имя пользователя никогда не становится ключом объекта (`safeObjectName`).

14 тестов, включая подделку расширения при честном MIME и path traversal.

### 1.8 Проверка подписи webhook без SDK

`src/lib/security/webhook.ts`. Из `builder-studio/lib/billing/provider.ts`.
Три обязательных свойства:

1. **constant-time сравнение** — обычное `===` позволяет подобрать подпись
   по времени ответа;
2. **окно защиты от реплея** — валидная подпись иначе действует вечно;
3. **подпись по СЫРОМУ телу** — `await request.json()` уже потерял порядок
   ключей, и подпись не сойдётся.

Функции чистые (`now` инжектится) → 13 тестов без сети, включая подмену
timestamp, подмену тела и чужой секрет.

Отсюда же переиспользован паттерн подписанных токенов без хранения в БД
(`signPayload`) — для ссылок подтверждения и приглашений инструкторов.

### 1.9 Turnstile с fail-open-когда-не-настроен

`src/lib/security/turnstile.ts`. Из `builder-studio/lib/turnstile.ts`:
**не настроен → пропускаем**. Это позволяет писать и тестировать защищённые формы
до получения ключей Cloudflare и не держать закомментированные вызовы в коде.
Настроен → проверка строгая, с таймаутом, никогда не бросает.

### 1.10 Защита экспорта от formula injection

`src/lib/security/export-safety.ts`. Из `builder-studio/lib/spreadsheet-safe.ts`.
Часто пропускаемая уязвимость: значение, начинающееся с `=`, `+`, `-`, `@`, tab
или CR, исполняется Excel как формула. В админке ArtDance экспортируются заказы
и отзывы — поля, полностью контролируемые клиентом.

Добавлено сверх источника: BOM в начале CSV (без него Excel читает UTF-8 как ANSI
и ломает армянский и кириллицу) и `;` как разделитель (Excel в локалях с запятой
как десятичным разделителем иначе не разбивает строку на колонки).

### 1.11 Кеш-политика по группам маршрутов

`src/config/cache.ts` + `next.config.ts → headers()`. Из `online-shop`.
Публичный каталог не содержит персональных данных в серверном HTML, поэтому CDN
отдаёт готовую оболочку и **не вызывает функцию** на повторных просмотрах — это
одновременно быстрее и дешевле.

Ключевая деталь реализации: **приватные маршруты идут ПЕРЕД каталогом**, потому
что Next применяет первое совпадение. Иначе `/hy/account` попал бы под правило
каталога из-за пересечения шаблонов и утёк в CDN. Список приватного ведётся
явно, а не по остатку — ошибка в эту сторону означает выдачу чужого заказа.

Проверено живьём: `verify:headers` требует `no-store` на `/hy/account` и
`s-maxage=180` на каталоге.

Оттуда же — именованные теги ревалидации (`cacheTags`): строковый литерал тега
в коде означает молча не инвалидированный кеш, худший вид бага.

### 1.12 Групповая валидация окружения

`src/config/env-report.ts`. Из `builder-studio/lib/env.ts`. `env.ts` падает на
обязательных переменных — это правильно. Но у необязательных интеграций другая,
более коварная проблема: **частично настроенная интеграция тихо не работает**.
Три из четырёх переменных R2 заданы — загрузка файлов молча падает в рантайме.

Проверка «всё или ничего» по группам, плюс сверка выбранного `PAYMENT_PROVIDER`
с наличием его реквизитов и отдельная ошибка на `mock` в production.
Функция чистая → 7 тестов.

### 1.13 Наблюдаемость и границы ошибок

- `instrumentation.ts` — единая точка startup-хуков с ветвлением по
  `NEXT_RUNTIME`. Динамические импорты: Node-only зависимости не должны попадать
  в Edge-бандл, иначе proxy перестаёт собираться с ошибкой про `node:fs`.
  `onRequestError` ловит исключения во вложенных RSC, которые не доходят до
  `error.tsx`.
- `src/app/global-error.tsx` — корневой layout упал, поэтому свои `<html>/<body>`,
  **инлайновые стили** (Tailwind мог не загрузиться), текст в разметке
  (провайдера переводов нет — единственное такое место в проекте), обычный `<a>`
  вместо `Link` (роутер сломан) и `error.digest` для сопоставления с логами.
- `src/app/[locale]/error.tsx`, `loading.tsx` — граница раздела и skeleton
  для streaming.
- Sentry: DSN отсутствует → SDK не инициализируется вообще. `beforeSend` вырезает
  cookie и `Authorization`, `sendDefaultPii: false` — адреса и телефоны клиентов
  не уезжают в трекер.

### 1.14 Health check двух уровней

`src/app/api/health/route.ts`. Из `office`, с уточнением:

- `GET /api/health` — liveness, **не трогает БД**. Если проверка живости зависит
  от базы, кратковременный сбой БД перезапускает все инстансы и превращает
  деградацию в полный отказ.
- `GET /api/health?deep=1` — readiness, проверяет БД с таймаутом 2 с, отдаёт 503
  при недоступности.

### 1.15 Бюджет размера бандла

`scripts/check-performance-budget.mjs`. Идея из `builder-studio`, реализация
переработана — оригинал считал сырой размер и не различал типы чанков.

Два отличия:

1. **Считаем gzip, не размер файла.** Пользователь скачивает сжатое; сырой размер
   завышен втрое и заставляет ставить бессмысленно большой порог.
2. **Разделяем начальную загрузку и ленивые чанки** по `build-manifest.json`.
   Начальный бандл влияет на LCP и держится в жёстких рамках (90 KB на чанк,
   260 KB суммарно). Ленивый чанк на LCP не влияет.

Этот бюджет сразу поймал реальную проблему: клиентский SDK Sentry (178 KB gzip)
попадал в начальный бандл каждой страницы, включая публичный каталог. Исправлено
динамическим импортом в `instrumentation-client.ts`. Текущая начальная загрузка —
**166 KB gzip**.

### 1.16 CI как воспроизводимый набор гейтов

`.github/workflows/ci.yml`. Из всех трёх проектов:

- `concurrency` с `cancel-in-progress` — новый пуш отменяет предыдущий прогон;
- **паритет локалей отдельным быстрым job'ом** (из `office`): падает за
  полминуты, а не после четырёхминутной сборки;
- сверка `tokens.css` с TypeScript-токенами — производный артефакт не должен
  расходиться с источником;
- сверка миграций со схемой — расхождение ловится в CI, а не при деплое;
- бюджет бандла и **проверка заголовков на живом сервере** — единственный способ
  проверить CSP и CSRF.

`lighthouserc.json` — разделение `error`/`warn` осознанное: регресс a11y, SEO и
best practices блокирует мерж, метрики скорости на CI-раннере шумные и только
предупреждают. Иначе команда привыкает игнорировать красный CI.

### 1.17 Развёртывание: Vercel + Supabase

Порядок операций не произвольный. `next build` пререндерит каталог, страницы
направлений и OG-картинки — то есть **обращается к базе во время сборки**. Схема и
демо-данные должны быть в облачной базе до первого деплоя, иначе сборка падает не
на конфигурации, а на пустых таблицах.

1. миграции: `npm run db:deploy` (по `DIRECT_DATABASE_URL`, session mode);
2. демо-контент: `npm run db:seed`;
3. переменные в проекте Vercel;
4. деплой.

Обязательный минимум переменных — `DATABASE_URL`, `AUTH_SECRET`,
`NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_APP_ENV`, `NEXT_PUBLIC_DEFAULT_LOCALE` и все
`NEXT_PUBLIC_FEATURE_*`. Флаги особенно: незаданный флаг читается как `false`
(`boolFlag` в `src/config/env.ts`), и магазин с событиями просто исчезают из
навигации — выглядит как потерянный раздел, а не как выключенная фича.
`DIRECT_DATABASE_URL` рантайму не нужен: он существует ради миграций, которые
запускаются с машины разработчика.

**Демонстрационный стенд объявляется как `preview`, не `production`.** В
`production` включается fail-closed: без `RATE_LIMIT_REDIS_URL`/`TOKEN` логин,
брони и платежи отклоняются (`src/lib/security/rate-limit.ts`), а mock-провайдер
платежей считается ошибкой конфигурации (`checkEnvironment`). При `preview`
лимиты работают в памяти, CSP пропускает оверлей `vercel.live`, а `robots.ts`
отдаёт `disallow: /` — демо не попадает в индекс. Цена решения названа честно:
`useSecureCookies` в Better Auth привязан к `isProduction`, поэтому cookie сессии
уходит без флага `Secure`. На HTTPS вход работает, но это компромисс стенда, а не
конфигурация продакшена.

Особенности Supabase, на которые уходит время, если о них не знать, описаны в
`.env.example` рядом со строками подключения: прямое подключение только по IPv6,
пароль в URL percent-кодируется, а `sslmode=require` без `uselibpqcompat=true`
обрывается на самоподписанном сертификате Supavisor.

Что на стенде не работает и это ожидаемо: **загрузка новых изображений**. Драйвер
R2 не реализован (ждёт ключи заказчика), а локальный драйвер пишет на диск,
которого в serverless нет. Демо-медиа отдаются из `public/media/seed`, то есть из
репозитория.

**Регион функций закреплён в `vercel.json`** (`"regions": ["hnd1"]`) и выбран по
расположению базы: проект Supabase создан в `ap-northeast-1`, а функции по
умолчанию поднимаются в `iad1`. Каждый запрос к базе тогда пересекал бы Атлантику
и Пацифику — на странице с несколькими запросами это заметно глазом. При переносе
базы в другой регион эту строку надо менять вместе с ней.

Наблюдение, оставленное открытым: на Vercel заголовки `Cache-Control` из
`next.config.ts` применяются к статическим ответам, но не к динамическим —
`/hy` приходит с `public, s-maxage=180`, а `/en/classes` с `no-store`, хотя
локальный `next start` отдаёт для обоих одно и то же. Приватные маршруты
остаются `no-store` в любом случае, то есть безопасность не затронута; страдает
только кеш каталога на CDN. Разбор — отдельной задачей: динамическая страница с
фильтрами в `searchParams` кешируется не заголовком из конфига, а стратегией
ревалидации на уровне самой страницы.

## 2. Что сознательно НЕ перенято

| Решение из проекта-источника | Почему отклонено |
|---|---|
| SQLite + Drizzle с идемпотентными миграциями на старте (`builder-studio`) | SQLite — single-writer, а маркетплейс с бронированием требует конкурентной записи. Взят PostgreSQL. Идея идемпотентных миграций несовместима с Prisma Migrate |
| Signed double-submit CSRF (`office`) | Origin-check достаточен и не требует хранения. Двух реализаций CSRF (как в `office`, где они дублируются в `csrf.ts` и `security.ts`) быть не должно |
| `containsSQLInjection` регексами, `sanitizeHTML` через regex-фильтр (`office`) | Эвристики, дающие ложное чувство защиты. Prisma параметризует запросы, HTML санитизируется библиотекой при появлении UGC-разметки |
| In-memory дедупликация webhook по `Map` с TTL (`office`) | Работает только внутри одного инстанса serverless. Дедупликация — в БД, уникальный индекс `(provider, eventId)` в `WebhookEvent` |
| Multi-tenant host routing и on-demand TLS (`builder-studio`) | У ArtDance один домен. Понадобится, если появятся кастомные домены студий |
| Ручное переключение `paymentStatus` из админки (`online-shop`) | Именно то, чего платформа с онлайн-оплатой делать не должна. Статус меняется только webhook'ом или сверкой |
| Списание склада сразу при создании заказа без резерва (`online-shop`) | В маркетплейсе с бронированием резерв обязателен: `SlotHold` с TTL и уникальным индексом на ресурс+время |
| Хардкод email как источник superadmin-прав | Классический account-as-backdoor. Источник истины — `role` в БД |
| Blanket `remotePatterns: '**'` для картинок | Превращает приложение в открытый прокси оптимизации изображений и открывает SSRF через `next/image` |

## 4. Аудит зависимостей

`npm audit` показывает 4 high. Все четыре — в CLI Prisma и в рантайм не попадают.
Оставлены осознанно, чтобы красный вывод аудита не выглядел недосмотром:

| Уязвимость | Где | Почему не исправляем |
|---|---|---|
| `deepmerge-ts` — исчерпание стека при слиянии рекурсивных объектов | `@prisma/config` → `prisma` (dev) | Срабатывает на конфиге, который пишем мы, а не пользователь. `npm audit fix` предлагает откат до `prisma@6.19.3` — это мажорное понижение с 7.10.0 и потеря driver adapters |
| `mysql2` — понижение auth-плагина до `mysql_clear_password` | `prisma` (dev) | Транзитивная зависимость CLI. Проект на PostgreSQL, этот код не исполняется никогда |

Оба пакета — `devDependencies`: они не попадают ни в клиентский бандл, ни в
серверный рантайм Vercel. Проверять при обновлении Prisma: как только выйдет
7.x с `deepmerge-ts@8`, обновиться и удалить этот раздел.

**Политика зависимостей:** версии фиксируются точно, без `^`. Диапазон означает,
что `npm ci` на CI и на машине разработчика могут собрать разные деревья, и
воспроизвести баг становится невозможно.
