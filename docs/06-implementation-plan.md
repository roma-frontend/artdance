Порядок работ от «клиент согласился» до продакшена. Задачи упорядочены по
зависимостям: следующая не начинается раньше, чем закрыта предыдущая в своей
цепочке. Отслеживание готовности компонентов — `npm run design:status`.

> Объём сверх макета — в `docs/07-feature-backlog.md`. Позиции с приоритетом **P0**
> входят внутрь задач этого плана (см. §7 бэклога) и должны учитываться **до**
> задачи 1.1: часть из них требует полей в схеме, а добавлять их после первой
> миграции дороже. Компоненты, которых нет в прототипе, — в
> `docs/08-component-catalog.md`; служебные модули — в `docs/09-helpers-catalog.md`.

Отбор: индексируемые условия в SQL, текстовый запрос в приложении (ключ поиска умеет транслитерацию, `ILIKE` — нет; уедет в индекс с 2.8), потолок `limits.query.maxRows`. `EventCardItem.startsAt` стал ISO-строкой: кеш данных сериализует значения. Инварианты хаба переехали из юнит-тестов в e2e — юнит-тесты обязаны работать без базы. **Поиск закрыт:** `queries/search.ts` читает публичный локализованный каталог, кеширует только конечные корпуса по locale и тегам, а транслитерационное ранжирование строк остаётся некешируемым. **Главная закрыта:** `queries/home.ts` валидирует локализованный `ContentBlock(key, locale)`, получает кураторский порядок и медиа из CMS, а карточки, публичность и счётчики — из Prisma; сид создаёт блок и самостоятельные MediaAsset для трёх локалей. **CI: у джобов сборки и e2e есть сервис Postgres с миграциями и сидом** — без базы сборка каталога не проходит. **Серверные операции бронирования очищены:** `booking/service.ts` больше не подставляет цену и расписание из фикстур; отсутствие занятия/профиля возвращает `NOT_FOUND`, пустое расписание — `SLOT_UNAVAILABLE`. Шесть изолированных тестов проверяют отказы, цену из БД (включая нулевую), стоимость выезда и перенос внутри реального расписания. **Календарь и альтернативы закрыты:** `content/booking.ts` читает публичный профиль и занятие, правила, исключения, блокирующие брони и активные удержания из Prisma без кеша; страницы и API ожидают асинхронный результат. `/booking` динамический. Удержание разрешает слаг в настоящий ID до проверки занятости и записи, учитывает буфер и больше не импортирует фикстуры. Предвыбор — первое свободное время; выезд — поле профиля, онлайн без данных не предлагается. **Переход с занятия привязан к ClassSession:** ссылка передаёт слаг занятия, календарь показывает реальные неотменённые проведения с ID и остатком мест; удержание проверяет соответствие времени и инструктора, бронь читает цену выбранного занятия. Списание места через условный `updateMany` и потребление удержания через `deleteMany` выполняются в одной транзакции — последнее место и повторный запрос не создают лишнюю бронь. Прямой вход от инструктора сохраняет индивидуальную сетку. Групповой экран не предлагает выезд и рекуррентную серию. Ограничение без миграции: уникальный индекс SlotHold допускает одно активное удержание группы за раз; подтверждённые участники той же группы не блокируют оставшиеся места. Браузерный сквозной сценарий ещё требует запуска на тестовой БД. **Атлеты переведены:** публичные профили, переводы, опыт и медиа из Prisma с тегом инструкторов; текстовая эвристика достижений сохранена до структурированного спортивного профиля. **Вспомогательные фасады очищены:** из `content/catalog.ts` удалены неиспользуемые фикстурные преобразователи, варианты сортировки занятий реэкспортируются из Prisma-слоя. `content/media.ts` читает MediaAsset с переводами, размерами, blur и focalPoint; при отсутствии кадра возвращает null без демо-подстановки. Страницы ожидают медиа, OG-рендерер получает ленивый загрузчик (без запроса к БД при импорте модуля). Правка медиатеки сбрасывает тег баннеров. Сид дополнен самостоятельными кадрами баннеров; его запуск на существующей БД ещё нужен и не выполнялся в этой задаче. Выбор кадра баннера пока остаётся картой в коде — перенос выбора в ContentBlock и UI-редактор `/admin/content` остаются задачей A-17 |

## Граница договора

Работа идёт по договору: **5 000 000 AMD за весь объём MVP, 3 календарных
месяца с момента начала работ, без аванса** — каждый этап закрывается актом
приёмки, оплата в течение 5 рабочих дней после демонстрации результата.
В договорную сумму входят три языка интерфейса (hy / ru / en) и QA-проход
перед запуском.

> Календарь с датами, ответственными и вехами — `docs/launch/mvp-schedule.md`.

Этапы договора ложатся на фазы этого плана так:

| Этап договора                | Сумма           | Фазы плана                                               |
| ---------------------------- | --------------- | -------------------------------------------------------- |
| 1. Требования и UX/UI-дизайн | 800 000 ֏       | Шаг 0 + дизайн-основание фазы 1                          |
| 2. Техническая основа        | 700 000 ֏       | Фаза 1 (инфраструктура, миграции, медиа, аутентификация) |
| 3. Каталоги и бронирование   | 1 200 000 ֏     | Фазы 2–3                                                 |
| 4. Магазин и оплата          | 900 000 ֏       | Фазы 4–5                                                 |
| 5. Управление и локализация  | 850 000 ֏       | Фазы 6–7 + языки hy/ru/en                                |
| 6. Приёмка и запуск          | 550 000 ֏       | Фаза 8 + QA-проход                                       |
| **Итого по договору**        | **5 000 000 ֏** | Шаг 0 — фаза 8                                           |

Вне договора и оплачивается отдельно:

- **Внешние сервисы** — домен, хостинг, эквайринг, SMS-шлюз, почта,
  мониторинг, отчёты об ошибках. Счета выставляют провайдеры напрямую
  заказчику (перечень и ориентиры — §10 договорного плана).
- **Всё из `docs/07-feature-backlog.md` сверх помеченного P0** — кошелёк,
  рефералки, абонементы, рекуррентные оплаты, push, бусты и прочее. Эти
  позиции оцениваются и договориваются отдельно, когда спросит рынок.
- Доработки после закрытия этапа 6 — по гарантии 30 дней (дефекты) или
  новым соглашением (новая функциональность).

Срок договора — 3 месяца — достигается параллелизацией фаз 2–5 и 6–7;
оценка «13–15 недель» ниже включает резерв, договорной срок жёстче.
