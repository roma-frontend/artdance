# DanceSport и пакеты занятий

Документ фиксирует бизнес-контракт реализованной структуры. Источником данных
остаётся Prisma-схема; подписи интерфейса живут в
`src/i18n/messages/{en,ru,hy}.ts`, а числовые правила и предложения — в
`src/config/`.

## DanceSport

- `DanceSportProgram`: `STANDARD` и `LATINE`.
- `DanceSportDiscipline`: пять дисциплин Standard и пять дисциплин Latine.
- `DanceClass.danceSportDiscipline`, `Course.danceSportDiscipline` и
  `Event.danceSportDiscipline` связывают каталог с точной дисциплиной.
- `InstructorProfile.danceSportDisciplines` хранит дисциплины преподавателя
  структурированно; свободные `specializations` остаются для педагогических
  уточнений вроде `Salsa On1`.
- `CatalogQuery.discipline` поддерживает URL-фильтр, например
  `/classes?discipline=quickstep`.

Стиль каталога (`BALLROOM`, `LATIN`, `TANGO`) сохраняется для обратной
совместимости и широкого фильтра. Точная дисциплина является более узким
фильтром и не заменяет стиль.

## Типы занятий

`LessonType` имеет значения `GROUP`, `PRIVATE` и `PAIR`.

- `DanceClass.lessonType` определяет формат предложения.
- `Booking.lessonType` фиксирует формат в истории бронирования.
- `PriceOption.lessonType` позволяет задавать тарифы индивидуально и в паре.
- Групповая сессия использует `CLASS_SESSION`; индивидуальная запись —
  `PRIVATE_SESSION`. Запланированный `PAIR` оформляется одной бронью на двоих:
  обязательное имя партнёра (`Booking.partnerName`), без аккаунта партнёра.
- Цена `PAIR` указана за пару; вместимость и `bookedCount` считаются в людях.
  Пара занимает два места и отменяется только целиком заказчиком.
- Запись напрямую у инструктора без выбранной сессии остаётся индивидуальной.
  Перенос запланированной сессии запрещён, пока нет выбора и атомарной
  резервации новой сессии; свободную индивидуальную запись переносить можно.

## Соревнования

`Event` типа `COMPETITION` может иметь:

- федерацию;
- окно регистрации;
- общие условия участия;
- `CompetitionCategory` с возрастной группой, программой, дисциплиной,
  условиями, взносом и лимитом заявок.

`CompetitionRegistration` связывает пользователя-атлета, соревнование и
категорию. Server Action проверяет:

1. аутентификацию;
2. открыто ли окно регистрации;
3. попадает ли возраст участника в диапазон категории;
4. не зарегистрирован ли участник повторно;
5. не исчерпан ли лимит категории.

При первой заявке создаётся `AthleteProfile`, а пользователю назначается роль
`ATHLETE`. Импорт календаря WDSF остаётся внешним интеграционным этапом: события
из официального календаря пока заводятся через админку.

## Пакеты занятий

Предложения находятся в `src/config/pricing.ts` (`cp-5`, `cp-10`, `cp-20`):
количество занятий, скидка и срок действия. Купленный пакет хранится в
`ClassPass`, остаток — `lessonsRemaining`, срок — `expiresAt`.

- покупка фиксирует реальную сумму пакета по базовой цене группы;
- `purchaseKey` защищает повторную отправку операции;
- активные пакеты показываются в кабинете;
- при выборе пакета на групповой брони списывается одно занятие;
- при бесплатной отмене списанное занятие возвращается;
- индивидуальные и парные брони пакет группы не принимают.

Миграция: `prisma/migrations/20261012120000_dancesport_structure`.

## Ограничения текущего этапа

- Создание пакета пока не связано с подтверждённым платежом. `pricePaid`
  хранит расчётную стоимость, а не доказательство оплаты; live-продажи требуют
  интеграции с платёжным сценарием.
- Публичное создание активных пакетов закрыто: обе Server Actions отказывают
  с `FEATURE_DISABLED`; каталог показывает поясняющий текст без кнопки. Внутренний сервис покупки
  не доступен как Server Action и оставлен для будущей платёжной интеграции.
- Списание проверяет владельца, срок, остаток и групповой формат. Остаток
  уменьшается условным `updateMany` внутри транзакции; отдельное списание
  блокирует бронь и не применяется к уже оплаченным занятиям.
- Отмена клиента и сотрудника использует условный переход статуса и версии
  записи, возвращает места по `participants` и предотвращает повторный возврат
  занятия. Поздняя отмена клиентом не возвращает занятие; возврат не продлевает
  срок пакета.
- Возврат клиенту рассчитывается по подтверждённым платежам с учётом уже
  оформленных возвратов, а не по номинальной цене неоплаченной брони.
- Имя партнёра пары поддерживается; приглашения второго аккаунта и полноценная
  связь партнёров в турнирной заявке остаются отдельным этапом.
- Программа занятия, курса и события выводится из дисциплины; отдельное
  редактируемое поле программы есть у категории соревнования.
- Старые записи не получили автоматический backfill дисциплин. Для атлетов
  структурированные значения имеют приоритет; при пустом поле используются
  старые специализации Standard и Latine.
- Платная активация подписок и списание их квот остаются отдельным этапом.
- На пустой тестовой PostgreSQL 17 применена вся цепочка миграций; проверка
  `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma
  --exit-code` не обнаружила расхождений. Shadow database этому варианту не нужна.
  Применение миграций к внешней БД не входит в локальные проверки кода.
- Перед запуском парных броней необходимо применить миграцию
  `prisma/migrations/20261012150000_pair_booking/migration.sql` и обновить
  Prisma Client. Эта миграция только добавляет nullable-поле имени партнёра;
  в рамках доработки к внешней БД она не применялась.
- Полный сценарий пары проверен Playwright на production-сборке и изолированной
  PostgreSQL 17: вход, удержание, создание, кабинет, отмена и повторная отмена.
- `scripts/verify-booking-db.ts` проверяет настоящие конкурентные транзакции:
  восемь списаний последнего занятия и восемь отмен допускают ровно одного
  победителя. Скрипт включён в schema job CI и требует явного
  `BOOKING_TEST_DATABASE_URL` на loopback-хост с именем БД, заканчивающимся `_ci`.
  Он удаляет только собственные probe-записи и отключает отправку реальных писем.

## Проверки перед push

- `npm run verify`: токены, CSS, переводы, медиа, видео, дизайн, типы, lint, unit.
- Пустая локальная БД: `prisma migrate deploy`, затем diff схемы как в CI.
- `BOOKING_TEST_DATABASE_URL=postgresql://…/artdance_ci node
  --conditions=react-server --import tsx scripts/verify-booking-db.ts`.
- На локальной БД с демо-сидом: build, perf:budget, verify:headers и Playwright,
  включая `e2e/pair-booking.spec.ts` для пары и unavailable-текста на трёх языках.
- Успех старых GitHub-запусков не проверяет незапушенные изменения. Итог нового
  Linux-прогона GitHub Actions можно подтвердить только после разрешённого push.
